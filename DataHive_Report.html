1. Distributed Systems Communication

1.1 Overview

The DataHive backend is architected as a distributed microservices system composed of three independent, loosely-coupled services. Each service owns its own responsibility, runs in its own Docker container, and communicates with other services either synchronously over HTTP/REST or asynchronously through a message broker (RabbitMQ). This design reflects real-world distributed systems principles including service isolation, fault tolerance, and asynchronous decoupling.

The three core services and their responsibilities are summarized below:

Service Container Name Port Responsibility
Authentication Service 519_auth_service 3001 User registration, login, and JWT token issuance
Event Service 519_event_service 3002 Create and view events; publishes events to RabbitMQ
Notification Service 519_notification_service 3003 Consumes RabbitMQ messages and logs notifications
PostgreSQL 519_postgres 5432 Persistent relational data store for users and events
RabbitMQ 519_rabbitmq 5672 / 15672 Message broker for asynchronous inter-service communication

1.2 Communication Patterns

The system employs two distinct communication patterns, each chosen deliberately based on the nature of the interaction required:

1.2.1 Synchronous Communication — REST over HTTP

Client-to-service interactions are handled via synchronous REST APIs built with Node.js and Express.js. When a client sends a request (e.g., to register a user or create an event), the service processes it and returns a response immediately. This pattern is appropriate for operations where the client needs an immediate result, such as authentication or data retrieval.

The REST endpoints exposed by each service are as follows:

Method Endpoint Service Description Auth Required
POST /auth/register Auth Service Register a new user No
POST /auth/login Auth Service Login and receive a JWT token No
POST /events Event Service Create a new event Yes (JWT)
GET /events Event Service Retrieve all events Yes (JWT)
GET /health All Services Health check endpoint No

1.2.2 Asynchronous Communication — RabbitMQ Message Queue

Service-to-service communication for event notifications is handled asynchronously via RabbitMQ, an industry-standard message broker implementing the AMQP protocol. This decouples the Event Service from the Notification Service — the Event Service does not wait for the Notification Service to process the message before responding to the client.

The asynchronous communication flow works as follows:

  1. A client sends a POST /events request with a valid JWT token.
  2. The Event Service validates the token, persists the event in PostgreSQL, and immediately responds to the client with a 201 Created response.
  3. The Event Service then publishes a JSON-serialized event message to the RabbitMQ queue named 519_event_queue with persistent: true to ensure message durability.
  4. The Notification Service, which maintains an open channel to RabbitMQ, receives the message asynchronously.
  5. The Notification Service logs the notification to the console and writes a JSON notification log file to the shared volume.
  6. The Notification Service acknowledges (channel.ack) the message, removing it from the queue.

The publisher implementation in the Event Service is shown below:

// 519_event_service/src/publisher.js
async function publishEvent(event) {
  channel.sendToQueue(
    QUEUE_NAME,
    Buffer.from(JSON.stringify(event)),
    { persistent: true }  // survives RabbitMQ restarts
  );
}

The consumer implementation in the Notification Service:

// 519_notification_service/src/consumer.js
channel.consume(QUEUE_NAME, (msg) => {
  const event = JSON.parse(msg.content.toString());
  console.log(`[NOTIFICATION] New event received: "${event.title}"`);
  // Write JSON notification log
  fs.writeFile(filename, JSON.stringify(notificationLog, null, 2), ...);
  channel.ack(msg);  // acknowledge message processed
});

1.3 JWT-Based Authentication Across Services

The system uses JSON Web Tokens (JWT) as a stateless, distributed authentication mechanism. When a user logs in via the Auth Service, a signed JWT is issued containing the user's ID, username, and email. This token is then passed by the client in the Authorization: Bearer <token> header on every subsequent request to the Event Service.

A critical distributed systems principle is demonstrated here: the Event Service validates the JWT independently without calling back to the Auth Service. Since both services share the same JWT_SECRET environment variable, the Event Service can verify the token's authenticity locally. This eliminates a synchronous inter-service dependency and prevents the Auth Service from becoming a bottleneck. 

// 519_event_service/src/middleware/auth.js
function verifyToken(req, res, next) {
  const token = req.headers['authorization']?.split(' ')[1];
  const decoded = jwt.verify(token, process.env.JWT_SECRET);
  req.user = decoded;
  next();
}

1.4 Container Networking — 519_network

All five containers are connected via a dedicated Docker bridge network named 519_network. Docker's internal DNS allows containers to resolve each other by their service name. For example, the Event Service connects to RabbitMQ at amqp://519_rabbitmq:5672 and to PostgreSQL at 519_postgres:5432 — without needing hardcoded IP addresses. 

# docker-compose.yml
networks:
  519_network:
    name: 519_network
    driver: bridge

1.5 Fault Tolerance and Retry Logic

In distributed systems, services rarely start at exactly the same time. To handle this, both the Event Service and Notification Service implement connection retry logic for RabbitMQ. If RabbitMQ is not yet ready, the service retries the connection every 5 seconds for up to 10–15 attempts before giving up. This prevents cascading failures during container startup.

Similarly, Docker Compose healthcheck configurations are defined for both PostgreSQL and RabbitMQ, ensuring dependent services only start after infrastructure is confirmed healthy: 

519_postgres:
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U datahive"]
    interval: 5s
    retries: 10

519_auth_service:
  depends_on:
    519_postgres:
      condition: service_healthy

2. Basic Analytical Data Ingestion Workflow

2.1 Overview

The DataHive system implements a simplified lakehouse-style data ingestion pipeline. The concept of a data lakehouse combines the raw data storage capabilities of a data lake with the structured querying capabilities of a data warehouse. In this implementation, every event creation triggers an ingestion workflow that persists structured JSON records to a shared storage volume — simulating how real-world analytical pipelines ingest transactional data for future processing, reporting, and analytics.

"Whenever a new event is created, the system stores event logs using JSON files for analytical/lakehouse-style ingestion." — Project Specification

2.2 Ingestion Architecture

The analytical ingestion pipeline consists of two parallel streams that are triggered simultaneously upon event creation:

Stream Producer Log Type File Pattern Purpose
Event Log 519_event_service Raw event record event_{id}_{timestamp}.json Source of truth for event data analytics
Notification Log 519_notification_service Notification receipt notification_{id}_{timestamp}.json Audit trail of notification delivery

Both streams write to a shared Docker volume named 519_logs, mounted at /app/logs inside the containers. This shared volume simulates a centralized data lake storage layer accessible by multiple services.

2.3 Ingestion Pipeline — Step by Step

Step 1: Event Creation (Trigger)

The pipeline is triggered when a client sends a POST /events request to the Event Service with valid authentication. The request body contains the event data:

POST http://localhost:3002/events
Authorization: Bearer <JWT_TOKEN>
Content-Type: application/json

{
  "title": "DataHive Launch",
  "description": "Company kickoff event",
  "location": "Karachi",
  "event_date": "2026-06-01"
}

Step 2: Persistence to Relational Database (Structured Storage)

The Event Service first persists the event to PostgreSQL, which serves as the structured, queryable layer of the lakehouse. The database record includes a system-generated ID and timestamp, creating an immutable record of the event:

INSERT INTO events (title, description, location, event_date, user_id)
VALUES ($1, $2, $3, $4, $5)
RETURNING *

Step 3: JSON Log File Write (Raw Data Lake Layer)

Immediately after database persistence, the Event Service writes a structured JSON log file to the shared volume. This represents the raw data ingestion layer of the lakehouse — an append-only, immutable log of all events in their original form, enriched with ingestion metadata.

The log file structure is:

// event_7_1747051234567.json
{
  "schema_version": "1.0",
  "source": "519_event_service",
  "ingested_at": "2026-05-12T10:30:00.000Z",
  "event": {
    "id": 7,
    "title": "DataHive Launch",
    "description": "Company kickoff event",
    "location": "Karachi",
    "event_date": "2026-06-01T00:00:00.000Z",
    "user_id": 3,
    "created_at": "2026-05-12T10:29:59.843Z"
  }
}

Key fields in the ingestion log:

  • schema_version — Enables forward compatibility as the schema evolves over time.
  • source — Identifies which service produced the log, critical for multi-service ingestion tracing.
  • ingested_at — The exact UTC timestamp of ingestion (distinct from the event's own created_at), supporting time-travel queries.
  • event — The complete, unmodified event record as stored in the database.

Step 4: Asynchronous Message Publication (Pipeline Trigger)

Simultaneously, the Event Service publishes the event to the 519_event_queue RabbitMQ queue. This message acts as a pipeline trigger, notifying downstream consumers that new data is available for processing — a core pattern in modern event-driven data pipelines:

// publisher.js
channel.sendToQueue(
  '519_event_queue',
  Buffer.from(JSON.stringify(event)),
  { persistent: true }
);

Step 5: Notification Service Consumption and Notification Log Write

The Notification Service asynchronously consumes the message from the queue. It processes the event and writes a notification log file to the shared volume. This log represents an audit trail of notification delivery and serves as a second, independent data stream for analytics — for example, tracking notification latency or delivery success rates:

// notification_7_1747051235890.json
{
  "schema_version": "1.0",
  "source": "519_notification_service",
  "notification_type": "event_created",
  "notified_at": "2026-05-12T10:30:01.234Z",
  "event": {
    "id": 7,
    "title": "DataHive Launch",
    ...
  }
}

2.4 Shared Storage Volume — Simulating a Data Lake

Both services write to a Docker named volume 519_logs, which is mounted into both the Event Service and the Notification Service containers at /app/logs. This simulates a centralized, shared object storage layer (analogous to AWS S3 or Azure Data Lake Storage in production environments). 

# docker-compose.yml
volumes:
  519_logs:
    name: 519_logs

# Mounted in both services:
volumes:
  - 519_logs:/app/logs

The resulting log files on the volume represent a continuous, append-only stream of JSON records that can be:

  • Queried with tools like Apache Spark or DuckDB for batch analytics
  • Streamed into a data warehouse such as Snowflake or BigQuery
  • Processed with Apache Kafka for real-time stream processing
  • Visualized in Apache Superset or Metabase dashboards

2.7 Key Design Principles

  • Append-Only Logs: JSON files are never overwritten — each event generates a new uniquely-named file. This ensures data immutability and supports time-travel analysis.
  • Schema Versioning: The schema_version: "1.0" field in every log entry enables future schema evolution without breaking existing consumers.
  • Separation of Ingestion Streams: Event logs and notification logs are kept separate, allowing independent analytics on event creation patterns vs. notification delivery performance.
  • Source Tagging: Every log entry carries a source field, enabling multi-service log aggregation and provenance tracking in a real data lake environment.
  • Dual-Layer Storage: The combination of PostgreSQL (for structured queries) and JSON files (for raw analytical access) mirrors the core lakehouse architecture principle of combining the best of data lakes and data warehouses.

3. Conclusion

The DataHive backend system successfully demonstrates two core principles of modern cloud-native engineering. The distributed systems communication layer employs both synchronous REST APIs for client-facing operations and asynchronous RabbitMQ messaging for inter-service event propagation, with JWT-based stateless authentication enabling secure, decentralized identity verification across services. The analytical data ingestion workflow implements a simplified but architecturally sound lakehouse pattern, using a dual-layer storage strategy of PostgreSQL for structured queries and append-only JSON file logs for raw data lake storage, both triggered through an event-driven pipeline.

Together, these components form a scalable, fault-tolerant, and production-aligned microservices architecture that fulfills the requirements of the DataHive Inc. platform specification while demonstrating mastery of distributed systems design, containerized deployment, and analytical data engineering fundamentals.
